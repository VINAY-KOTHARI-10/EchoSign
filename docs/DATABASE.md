# Database design

EchoSign uses two databases on purpose, with a clear source of truth for each kind of data.

## Who owns what

| Database | Holds | Why |
|---|---|---|
| **PostgreSQL** (Prisma) | users, profiles, classrooms, **captions**, class members (attendance), practice sessions, chat messages, languages, achievements, audit log | Relational data with foreign keys, transactions and ordered queries. **Source of truth** for anything a person might need to rely on later (a transcript, attendance, statistics). |
| **MongoDB** (Mongoose) | login sessions (hashed refresh tokens), one-time login codes, the practice activity feed (`UserActivity`) | Short-lived or document-shaped data. Sessions and codes **expire by themselves** (TTL indexes). |

### Partial writes between the two

Registration and practice sessions touch both. The rule is: **write PostgreSQL first, treat MongoDB as repairable.**

- A practice session and the profile statistics are written in **one PostgreSQL transaction**. Statistics are *recomputed* from the session rows (count, average, sum), never incremented, so retries cannot double count.
- The MongoDB activity feed update is best effort. If it fails the session is still saved and a warning is logged.
- `npm --prefix backend run maintenance -- reconcile` reports drift (statistics that disagree with the rows, users without an activity document or profile). Add `--apply` to repair. It is safe to run any time, as often as you like.

## Captions: the model

```
Caption(id, classroomId, speakerId, speakerName, source, text, createdAt,
        originalText, editedAt, editedById, clientId)
        UNIQUE(classroomId, clientId)        -- the idempotency key
        INDEX(classroomId, createdAt), INDEX(classroomId, speakerId)
```

- `clientId` is generated by the sender for each caption. A retry carries the same id, the unique index rejects the second insert, and the server returns the stored caption. NULLs do not collide, so older clients without an id still work.
- `speakerId` and `speakerName` come from the authenticated user, never from the request.
- `createdAt` is stamped when the server *receives* the caption, because database writes can finish out of order.
- Edits keep `originalText`, the editor and the time.
- Pages are ordered by `(createdAt, id)` and use cursors, so there is no fixed cap and no skipped or repeated rows.

## Attendance

`ClassroomMember(classroomId, userId, role, joins, reconnects, totalSeconds, firstJoinedAt, lastSeenAt, lastLeftAt)`, one row per person per class.

- A person is counted once however many devices they use; they "leave" only when the last device leaves.
- `joins` counts visits, `reconnects` counts returns after a departure, `totalSeconds` is saved every minute and finalised when the last device leaves or the class ends.

## Indexes added for the new features

`captions(classroomId, clientId)` unique, `captions(classroomId, speakerId)`, `classroom_members(userId)` (the student library), `classrooms(active, createdAt)`, and `audit_logs(createdAt | actorId | action)`.

## Migrations

- Only **additive** migrations are added; an applied migration is never edited. The newest, `20261114000000_classroom_reliability_audit`, adds columns, indexes and the `audit_logs` table and changes no existing data.
- `npm --prefix backend run test:migrations` proves, in throwaway schemas:
  1. all migrations apply to an empty database and match `schema.prisma`;
  2. the newest migration applies on top of a database populated in the *old* shape, losing no rows, with new columns defaulting to NULL / 0, NULL `clientId`s allowed, duplicate `clientId`s refused;
  3. your real tables are unchanged (row counts compared before and after).
- Known and harmless: an older migration created a `refresh_tokens` table that `schema.prisma` no longer declares (refresh tokens now live in MongoDB). It is left alone.
- Deploys run `prisma migrate deploy` automatically before the server starts (`npm run start:migrate`).

## Safe user deletion

Deleting a user (admin) removes their PostgreSQL rows (sessions, messages, profile, achievements) and their MongoDB login sessions, codes and activity document. A teacher who hosts classes is **not** deleted until the admin confirms, because their classes and transcripts go with them. The last admin can never be deleted or demoted. Every deletion and role change is written to the audit log.

## Retention

| Data | Rule |
|---|---|
| Login sessions, one-time codes | Expire automatically (MongoDB TTL). |
| Audit log | Kept `AUDIT_RETENTION_DAYS` (default 365). |
| Classes, captions, attendance | Kept until deleted, **unless** you set `CLASS_RETENTION_DAYS`, which removes *ended* classes older than that. |
| Practice sessions, chat | Kept until the user is deleted. |

Apply with `npm --prefix backend run maintenance -- retention` (a dry run) and add `--apply` to delete. Nothing is deleted automatically.

## Backups

- **Neon (PostgreSQL):** turn on point-in-time restore (history retention) in the Neon console, and take a manual copy before risky changes: create a branch, or run
  `pg_dump "$DIRECT_URL" --no-owner --format=custom --file=echosign-$(date +%F).dump`. Restore into an empty database with `pg_restore --no-owner --dbname "$NEW_DIRECT_URL" echosign-DATE.dump`.
- **MongoDB Atlas:** enable Cloud Backup on a paid tier, or export with `mongodump --uri "$MONGODB_URI" --out backup-$(date +%F)`. Losing MongoDB signs everyone out and clears pending codes, but loses no classroom data.
- **Before a deploy that changes the schema:** take a Postgres dump first. Test a restore at least once; a backup you have never restored is not a backup.
- Keep dumps private: they contain email addresses and password hashes.

## Connection handling

Prisma uses the pooled (`DATABASE_URL`) connection for the app and the direct one (`DIRECT_URL`) for migrations. The server disconnects both databases on shutdown. `GET /health/ready` checks both; `GET /health/live` checks only that the process is up.
